## Performance gates and measurement

Proposed normal test profile **N1**: 4 Mbps download, 1 Mbps upload, 150 ms added round-trip latency, zero induced packet loss. Apply shaping at the browser/network boundary to all dependencies, including redirects. Use a fixed reference runner with Chrome CPU slowdown 4×, mobile viewport 390 × 844 CSS pixels, device scale factor 2, and touch enabled. Record runner CPU/OS, browser/tool versions, shaping method, and measured unshaped RTT; do not describe emulation as a physical-device result. Q1 must freeze this runner and the load-generator/client region after Q5/Q6 select service locations. Use the intended launch region with the highest measured RTT if several markets are supported.

| ID / journey | Start → completion boundary | Proposed N1 release budget |
| --- | --- | --- |
| P1 Page load | Navigation start → LCP; separately, visible primary controls are enabled and session resolution reaches the correct state | p75 LCP ≤ 2.5 s; p95 usable ≤ 4 s; p75 CLS ≤ 0.1 on each of landing, sign-in, own-profile, and protected deep-link loads |
| P2 Authentication | Submit valid credentials → authorized destination rendered with session resolved; verified first login also includes atomic provisioning | p95 ≤ 3 s, separately for existing and first-login users; include provider round trips and redirects |
| P3 Profile save | Submit valid changed display name → server commit acknowledged and saved name/version rendered | p95 ≤ 1.5 s; reload and subsequent sign-in must show the committed value; optimistic rendering is not completion |
| P4 Navigation | Activate an in-app destination → destination heading/content or honest placeholder rendered, focus updated, and required authorization complete | p95 ≤ 1 s on each core route transition; pending indicators do not count as completion |
| P5 Interaction feedback | User action → visible pending/pressed response; keyboard and assistive-technology feedback must agree | p95 ≤ 100 ms; measured interaction latency p75 ≤ 200 ms across the scripted core journeys |

Authentication timing excludes human typing, reading email, and user verification delay, but includes all machine work after submit. Separately measure sign-up/recovery request acknowledgement, valid verification/reset confirmation, and sign-out/revocation at p95 ≤ 3 s each. Delivery of test verification/recovery email must reach the controlled inbox within 60 s in all 10 trials; report delivery separately from P2. Use synthetic accounts and a controlled inbox. Never bypass production security checks to obtain a passing time.

Measurement protocol, owned by SUR-13:

1. Use a production build on production-equivalent staging tiers/configuration with actual selected auth/database/email services and synthetic data. Record commit, configuration/migration revision, regions, exact test versions, dataset size, timestamps, and third-party limits. No mocks in release evidence. Seed 1,000 synthetic accounts/profiles, following SUR-4's proposed 1,000 MAU envelope; validate it under Q1.
2. For P1, run 30 cold-browser navigations **per route** with empty browser cache/storage (provision the required synthetic session out of band for protected pages), plus a separate 30-run repeat-visit cohort. Record CDN/cache state and server cold starts. For P2–P5 run 30 trials per scenario/transition with declared session/cache state; separately exercise stale-session and first-request-after-idle paths. Do not discard slow attempts or pool routes/cache states.
3. Calculate nearest-rank percentiles: sort the samples and select rank `ceil(p × n)`; for 30 samples p75 is rank 23 and p95 is rank 29. Report sample counts, p50/p75/p95/max, failures/timeouts, and raw redacted samples. Failed attempts remain failures and cannot disappear from the report; all 30 valid-path trials must succeed in addition to meeting timing gates. Expected denial cases are tested separately.
4. Repeat the timed cohorts under a 15-minute background workload of 20 concurrent active synthetic users producing 10 aggregate application requests/second after a two-minute ramp. Mix 60% profile reads, 20% profile saves, and 20% session checks; include session lookup/refresh/revocation costs. Foreground cohort requests are additional and reported. Background unexpected errors must be ≤ 1%, with zero authorization, corruption, duplicate-provisioning, or false-save defects. Respect approved provider rate limits; rate limiting valid expected traffic is a capacity failure, not a sample exclusion.
5. Corroborate P1–P4 with 10 N1 trials per journey on physical iPhone SE (3rd generation) and Pixel 6a (or Q2-approved equivalents), recording exact OS/browser. Require every trial to meet the corresponding time limit; report separately from emulated percentiles. SUR-12 covers functional behavior on the full matrix below.
6. Attach redacted traces, scripted steps, aggregate results, and defects to the release evidence. A failure blocks release until fixed and the affected cohort rerun. A different region, provider tier, auth/session contract, or material bundle change requires affected measurements again. Lighthouse scores alone do not establish these gates.

Additional network cases for every core journey: **N2** unshaped stable broadband (record observed throughput/RTT); **N3** degraded 400 Kbps down/100 Kbps up, 400 ms added RTT, 1% packet loss; **N4** offline before submit, during save, and during sign-out, followed by reconnection. N1 budgets do not apply to N3/N4. Under N3 a pending state appears within 100 ms and an operation completes or provides a safe retryable/unconfirmed outcome within 15 s. Under N4 show loss-of-connectivity or unconfirmed outcome within 15 s of the action. No false save/sign-out success, blind mutation retry, unauthorized cached content, or lost authorized draft on transient failure; expiry/logout still clears identity-scoped drafts. SUR-5 A6/A7/A10/A11 govern reconciliation and failure behavior.

Any known applicable A/AA failure blocks release under the approved target. Q2 must explicitly accept the target; this document makes no certification or completed conformance claim.

## Availability, recovery, environments, and ownership

Proposed service objective: **99.5% monthly availability**, continuously measured for sign-in/session resolution, profile read/save/readback, and core navigation. Probe each journey every minute from two independent locations representative of approved launch markets, with dedicated synthetic users and N2 conditions. An eligible minute is good only if every journey succeeds from both locations within 15 s, including persistence/authorization checks. Missing results count as bad unless an independently evidenced probe-only failure is documented; disclose excluded probe minutes. Availability is good eligible minutes / all eligible minutes in the calendar month. Planned maintenance and provider incidents count as downtime. For a 30-day month with no exclusions, the budget is 216 minutes. This is an internal objective, not a customer SLA or vendor guarantee; latency gates remain separate.

SUR-13 must demonstrate alert delivery after two consecutive failed probe minutes and actionable, redacted diagnostics. Q3 must name primary and backup responders and approve coverage; proposed coverage is 24/7 paging, acknowledgement within 30 minutes, incident updates hourly until recovery. Acknowledge/restore timing starts at the first failed probe, or earlier incident report. If this coverage cannot be staffed, revise the objective explicitly before launch. A new launch uses staging probe/alert evidence; the first production monthly report is retrospective, not a fabricated pre-release result.

## Data obligations and retention decisions

Q6 requires a factual applicability assessment by a named qualified privacy/legal reviewer and the accountable product owner. Do not infer jurisdiction from a chosen cloud region. Record the operating legal entity/controller, establishment, intended and excluded launch markets, user age policy, categories/purposes of processing, and vendor relationships. Determine applicable privacy, consumer, cookie and child-protection rules, any registration/notice duties, residency/cross-border transfer restrictions, processor agreements/subprocessors, and rights/incident response deadlines. An applicability or non-applicability conclusion must include rationale, reviewer, date, and supporting evidence. No regulatory regime or certification is assumed here.

Proposed lifecycle defaults below are engineering inputs for Q6, **not approved legal deadlines**. If an applicable requirement or processor capability conflicts, revise the policy and implementation before collecting real personal data.

| Category | Proposed limit / trigger | Required implementation and evidence |
| --- | --- | --- |

| Account deletion | Deny access/revoke sessions immediately on an authorized deletion request; erase live app/profile/Auth data and initiate processor deletion within 30 days. Essential auth/session storage must have a documented purpose and notice. Q6 must determine whether local rules require consent or another lawful basis for each purpose; an essential cookie label is not a legal conclusion. No optional analytics, advertising, marketing email, or non-essential tracking is included. Adding one requires a processor/purpose review and any required prior opt-in, refusal, withdrawal and evidence-of-consent handling. Sharing consent/visibility controls belong to the privacy project, remain explicit and private by default, and do not substitute for account-processing notices or lawful basis.

Foundation responsibility: SUR-7 secures configuration/regions/processor settings; SUR-8 implements retention, deletion propagation and restore safeguards; SUR-9 handles identity/session lifecycle; SUR-10 minimizes and protects profile data; SUR-13 controls telemetry; SUR-14 validates security and recovery. The privacy project owns activity-sharing/withdrawal semantics and propagation into streaming/social/discovery. Logan must assign any cross-project or legal-policy work to a named owner and linked deliverable under Q6/Q7 before production; “privacy project” alone is not an accepted assignment.
