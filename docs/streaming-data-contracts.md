# Streaming data contracts and acceptance targets

## Scope and evidence boundary

This proposal defines streaming-owned interfaces and test requirements for SUR-19 through SUR-27. It builds on the [account/profile contract](account-profile-contracts.md) and [foundation quality/data-handling requirements](quality-gates-and-data-handling.md); their open decisions remain open. It does not change application identity, authentication, foundation budgets, visibility, or legal policy. “Must” and numbers below describe behavior proposed for approval, not implemented behavior, measurements, or accepted commitments.

Reviewed on 2026-10-30: the [streaming PRD](https://linear.app/lb-sandbox/project/streaming-connections-and-viewing-activity-sync-3d5b951b37ac), [SUR-16](https://linear.app/lb-sandbox/issue/SUR-16) and its comments/attachments, SUR-17, SUR-18, SUR-22, SUR-23, SUR-27, and the two foundation documents. No provider feasibility report, representative authorized provider sample, approved catalog, or target sign-off was available in those sources. SUR-6's tracker status is Done, but its document explicitly leaves Q1–Q7 pending; tracker status is not evidence of approval.

## Ownership, connections, and subscriptions

Foundation `appUserId` is the immutable owner of every streaming record. A streaming account and a provider viewing profile are separate from the one foundation own-profile; neither creates another application identity. The server derives the actor and checks ownership on every read/write/job. Provider email, display name, or household membership never proves application identity or grants visibility. All imports and connection metadata are private under SUR-5; sharing is a separate privacy decision.

Proposed multiple-account policy: allow multiple accounts per provider per application user, with a launch capacity of three accounts per provider. Each connection represents exactly one provider account. Enforce uniqueness of `(appUserId, providerNamespace, providerAccountKey)` where stable account identity is verified; reconnect updates the existing connection and preserves its identity. A connection ID is never a substitute for deduplication across reconnects. Without verified stable identity, block automatic account linking/reconnect reconciliation pending S1; do not guess from an email. The same external account linked by two app users remains two isolated datasets, with no cross-user merge or disclosure. Whether that use is permitted requires SUR-16/SUR-18 review.

For profile-scoped history, require explicit selection of one provider profile per connection for the initial release; switching profile creates a distinct import scope and cannot relabel existing history. Importing several profiles on one connection is deferred. If data is only account-scoped, label it “account activity; viewer unknown,” require acknowledgement before import, and never attribute it to a particular household member. If mixed-profile records cannot be filtered reliably, do not silently import them as the selected profile. Missing profile IDs on profile-scoped rows are quarantined. Profile labels are presentation only; labels changing must not change ownership or scope.

All contracts below carry `schemaVersion: 1`. IDs are opaque strings; enums are closed; nullable means unknown/absent, not false. Reject unknown mutation fields. Server timestamps use RFC 3339 UTC with `Z`; provider timestamps follow the separate precision rules below. These are logical contracts, not existing endpoints or database schemas.

| Contract / field | Required meaning and invariant |
| --- | --- |
| Connection identity | `connectionId`, `appUserId`, `providerNamespace`, `providerAccountKey` (opaque provider-scoped key, never email), `version`, `createdAt`, `updatedAt`. Namespace includes service and environment; region where identifiers require it. Account key may be null only before verified authorization; no import until resolved. |
| Import scope | `scopeId`, `connectionId`, `scopeKind: account \| profile`, `providerProfileKey` (required for profile; null for account), optional private label, `selectedAt`, `selectionVersion`. Source identity includes this immutable scope. A changed selection stops old-scope jobs, preserves labelled history subject to policy, and starts a separate checkpoint. |
| Authorization | `state: disconnected \| authorizing \| connected \| action_required`, `authorizedAt`, `lastValidatedAt`, `grantedScopes`, server-only `credentialRef`, monotonic `authorizationGeneration`, safe `reasonCode`. Tokens never appear in owner projections, events, fixtures, or logs. |
| Connection transitions | Start authorization → authorizing; verified callback with required scopes/account → connected; expired/revoked access → action_required; disconnect → disconnected. Callback failure restores the prior valid state or disconnected with a safe error. Reconnect must prove the same account or explicitly create a separate connection. |
| Revocation/disconnect fence | Stop scheduling immediately; increment authorization generation and invalidate credential access. Check active app user, connection generation, selected scope/version before fetch and again atomically before commit. Late callbacks/jobs cannot resurrect access or commit. Provider revocation is attempted where supported; record pending/failure honestly. |
| Sync state (separate from connection state) | `idle \| queued \| running \| partial \| succeeded \| failed \| canceled`; `runId`, trigger (`initial \| scheduled \| manual \| retry`), server-owned checkpoint, `startedAt`, `finishedAt`, `lastAttemptAt`, `lastSuccessfulSyncAt`, `nextEligibleAt`, safe error and retryability. Connected does not mean synchronized. |
| Coverage | Requested and accessible window with nullable bounds and `boundsStatus: known \| unknown`; scope, snapshot/watermark if available, pages/rows read, new/updated/duplicate/quarantined counts, `coverageState: unknown \| partial \| complete`. Complete means all accessible pages in the declared window reconciled, never lifetime completeness. Unknown bounds cannot be presented as full history. |

Connection operations use expected versions and idempotency keys. Concurrent refresh requests coalesce to one scope job; only one job per connection executes at a time. Checkpoint updates and row outcomes commit atomically, or use an equivalent durable replay protocol. A crash after commit before acknowledgement must not duplicate data. A failed page leaves the run partial even when earlier pages are visible. `lastSuccessfulSyncAt` advances only when the declared accessible window finishes; a run with quarantined rows must expose their count and degraded data quality even if retrieval completed. A scope change never advances the old scope's checkpoint. Safe errors reuse SUR-5 conventions and add reasons such as `ACCESS_REVOKED`, `SCOPE_UNRESOLVED`, `PROVIDER_RATE_LIMIT`, `SOURCE_CHANGED`, and `RETRY_EXHAUSTED` without raw provider payloads.

A subscription is an account entitlement observation, not a connection flag or a foundation profile field:

| Field | Contract |
| --- | --- |
| Identity | `subscriptionObservationId`, `connectionId`, `appUserId`, provider namespace; observations belong to the account, not the selected viewing profile. |
| `state` | `active`, `inactive`, `unknown`, or `unavailable`. Active/inactive require explicit authorized evidence. Unknown means supported but not known/current; unavailable means verified unsupported or scope does not permit it. Unverified providers remain unknown. |
| `basis` | `provider_reported`, `not_observed`, `not_supported`, or `not_permitted`; include evidence reference and safe limitation reason. Do not infer active/paid from a successful login, playback record, or recent sync. User assertions are outside v1. |
| Optional evidence | `entitlementKind`, `planName`, `billingCadence`, `renewsAt`, `endsAt`, and `isPaid` are individually nullable with field availability/reason metadata. Trial, bundle, household access and paid plan are distinct only if explicitly reported. No billing or cancellation operations. |
| Observation time | `observedAt` (server retrieval), optional `effectiveAt` and provider `validUntil`, plus `staleAfter` from the provider-approved policy. After expiry, present unknown with the last observation marked stale; provider outage/disconnect is not inactive. If no validity rule is agreed, do not label an old observation current. |

## Canonical catalog and event contract

Proposed catalog direction for S2: evaluate **TMDB movie and TV episode identifiers** as the first matching source. This is a candidate selection, not evidence of licensing, API availability, coverage, or approval. Before SUR-22 binds to it, catalog/product/privacy reviewers must confirm terms, caching/attribution, regional/language coverage, episode numbering/specials, quotas, cost, and discovery interoperability against provider samples. If it fails, explicitly select another catalog and revise S2; no title-string identity fallback. The catalog's own identity rules remain separate from application user identity.

Use internal stable `catalogEntityId` values for movies and episodes, with versioned crosswalks to `(catalogNamespace, entityType, externalId)`. An episode's mapping includes its series and catalog episode ID; season/episode numbers alone are insufficient (specials and reordered releases exist). A series-only record cannot become an episode. Catalog remapping changes the match revision, never the event ID or its source identity.

| Contract / field | Required meaning and invariant |
| --- | --- |
| Event identity | `eventId`, `appUserId`, `scopeId`, `eventKind: viewing_observation`, `mediaKind: movie \| episode \| unknown`, `createdAt`, `updatedAt`, `normalizationVersion`. One event represents one distinguishable source occurrence; it does not assert completed playback or a unique human viewing session. |
| Source identity | Provider namespace, account key, scope, and provider event ID when verified stable. If event IDs are unique only per title, include that documented namespace component. Persist the source-key recipe/version. Without an event ID, follow the ambiguity rules below. Never include catalog match, run ID, retrieval time, or connection credential generation in event identity. |
| Source attributes | Nullable `providerTitleId`, source title, media type, year, series/season/episode labels/numbers, progress/duration/completion. Keep only approved necessary fields, each with availability/reason. A title label is not a canonical identifier; absent completion stays unknown. |
| Provenance | Every event has at least one source observation: `observationId`, source key, `connectionId`, `scopeId`, `runId`, opaque page/row locator, `firstSeenAt`, `lastSeenAt`, `retrievedAt`, adapter version, permitted payload digest and normalization/match revisions. Retain observations when evidence-backed duplicates are linked. Raw payload is optional, access-controlled, and subject to SUR-18, never required indefinitely. |
| Catalog match | `matchState: matched \| ambiguous \| unmatched \| unsupported`; nullable catalog reference, match method, matcher/crosswalk revision, `evaluatedAt`, safe reason, and candidate references for ambiguity. Matched requires a single evidence-supported movie/episode identity; every other state has null canonical identity. |
| Match methods | `verified_crosswalk` for a reviewed identifier mapping; `metadata_rule` for a uniquely validated combination of type/title/year or series/episode evidence. Title alone, series alone, popularity or a score without calibration cannot force a match. Numeric confidence is optional and only meaningful with a calibrated method/version. |
| Matching failures | Ambiguous = multiple plausible candidates; unmatched = no sufficient candidate; unsupported = content type outside movie/episode scope. Catalog outage is a retryable evaluation error with last match retained (or unmatched with `CATALOG_UNAVAILABLE` if never evaluated); it is not evidence that a title does not exist. |
| Presentation | Preserve unmatched/ambiguous records privately with source label and explicit unknown date/identity. Never silently drop them to improve accuracy metrics. Do not feed unresolved identities to canonical title aggregates. Keep unresolved duplicate groups distinguishable from confirmed repeats. |

### Timestamp semantics

Store `occurredAt` only for a verified instant, normalized to UTC; otherwise null. Also store `timePrecision: instant | date | unknown`, `sourceLocalDate` for a date-only value, nullable IANA zone/explicit offset when supplied, `timeBasis: provider_reported | unavailable | invalid`, and a safe source-time representation needed for normalization. Never invent midnight UTC, use retrieval time as watch time, infer timezone from server location, or guess which side of a daylight-saving fold applies. An offset-free local datetime without a verified zone/ambiguity rule has unknown instant; it may retain its date with date precision. Invalid/future values outside documented provider tolerance retain a validation reason and no invented instant.

`retrievedAt`, `firstSeenAt`, `lastSeenAt`, import completion, and subscription observation time describe ingestion, not viewing. Source timestamps may describe start, end, update, or an unspecified activity date; record `providerTimeMeaning` and do not compare unlike meanings as exact watch times. Unknown-date events sort in an explicit undated group; date-only events display as dates without fabricated time ordering. Timestamp corrections update the same stable-ID event and provenance revision.

## Repeated watches, replay, and overlap

Idempotency is scoped to the same application owner, provider account, and selected import scope. Never deduplicate across app users or different provider profiles. Content identity and viewing-event identity are different.

| Evidence | Required outcome |
| --- | --- |
| Same stable provider event ID on retry, overlapping page/window, or reconnect | Upsert one event and update observation/revision; no new event. A corrected timestamp/title does not create a repeat. Conflicting payloads require provider revision ordering or explicit conflict; last network arrival is not proof of source order. |
| Different stable event IDs for the same movie/episode | Preserve separate observations, including identical or missing timestamps. Treat as separate occurrences unless the provider documents alias/replay semantics; never collapse merely because times are close. |
| No stable ID; provider verifies a unique composite occurrence key | Use the versioned provider-specific key (for example title ID + exact start time + session discriminator), proven against repeat-watch samples. Precision alone is insufficient to establish uniqueness. |
| No occurrence key, but stable source artifact/snapshot and row locator | Same artifact digest + row locator replay is idempotent; identical rows at different locators remain separate source observations. Record `identityQuality: artifact_local`. Across changed/overlapping artifacts, preserve uncertain observations with `duplicateState: unresolved`; do not silently merge or count them as confirmed unique watches. |
| Missing/coarse timestamps and no stable occurrence/row identity | Quarantine with `SOURCE_IDENTITY_UNRESOLVED`, retain an approved minimal diagnostic, and report incomplete normalization. Do not hash title/date alone, assign fresh IDs on every retry, or fabricate a timestamp. SUR-16 must supply a supported reconciliation strategy before this provider can pass. |
| Same canonical title/time from different providers or accounts | Preserve separate events and provenance; mark possible overlap as unresolved, not a proven duplicate or repeat. No automatic time-window merge. Similarity can identify review groups but cannot authorize deletion or reduce confirmed counts. |
| Cross-provider shared origin-event reference, documented and verified for both sources | Within the same app user and compatible scope attribution, map the verified origin key to one event with both observations. Keep stable event identity and an alias if two existing events are reconciled. Never merge based only on matching title, account labels, or time. Without such evidence, use the preceding rule. |

`identityQuality` is `provider_stable`, `verified_composite`, or `artifact_local`. `duplicateState` is `distinct`, `confirmed_same_event`, or `unresolved`; distinct means distinguishable source occurrences under the evidence available, not proof of distinct human sessions. Counts must separately expose canonical events, source observations, and unresolved overlap groups. Preserve unresolved cases through reprocessing; matcher upgrades cannot erase repeats. Any supported source deletion or correction must be reconciled explicitly under provider semantics and SUR-18; absence from a later retention-limited page is not a deletion instruction.

## Backfill, cadence, refresh, and recovery

Proposed evaluation profile B1: initial import requests all authorized history in the latest **365 days**, capped at **10,000 source records per selected scope**. Use a fixed run cutoff and record accessible bounds. If the provider exposes less history, disclose that exact bound; if more than the cap exists, report truncation and partial coverage rather than success for the requested window. Do not mark a cap-limited import complete. Undated records returned in that retrieval are retained in an undated coverage bucket and count toward the record cap and reconciliation denominator; they cannot be claimed to fall within the 365-day window. Date-only records follow the provider calendar boundary, with boundary uncertainty disclosed. A provider returning only a latest-N snapshot cannot promise older history. SUR-16/S3 must accept or replace B1 separately for each verified provider before adapter acceptance.

Proposed ongoing policy: poll every **6 hours**, with up to **15 minutes positive jitter**, and re-read **7 days** of overlap to capture late records/corrections. Prefer verified incremental cursors when available, while retaining the approved reconciliation window. A date-only source uses its documented calendar semantics; do not assume UTC boundaries. Cadence/window values require evidence of publication delay, quota, retention, and correction lag. Records later than the overlap window require a provider-specific reconciliation/backfill policy, not a false no-loss promise. No scheduled polling for a manual-export-only source; any such launch scope requires an explicit alternate contract and freshness label.

Manual refresh requests the same incremental operation, coalesces with queued/running work, and has a proposed **15-minute per-connection cooldown**; it cannot bypass quota, revocation, or backoff. Return accepted run ID or safe `nextEligibleAt` promptly; never imply immediate freshness. A full reimport is a separate controlled recovery operation, not a refresh side effect.

Proposed transient retry budget: at most **5 attempts per page** (initial + 4 retries), exponential backoff starting at 5 seconds capped at 5 minutes with jitter, honoring any longer provider Retry-After. Persist delayed work instead of holding a worker; scheduling still counts toward latency. After **24 hours** elapsed for a run, stop with partial/failed status and actionable retry evidence. Expired/revoked credentials require action, not blind retries. A later authorized recovery resumes the checkpoint or restarts safely if cursors expire; a source snapshot change invalidates unsafe cursors explicitly. Per-provider queues/quotas isolate failures so one provider cannot consume all workers. Backfill/retry limits and actual scheduling infrastructure remain S3/S4 decisions.

Disconnect immediately stops new imports; historical retain/delete behavior, raw-data retention, revocation cleanup and account-deletion propagation are explicitly **unresolved in SUR-18**. This document does not select a retention default or authorize collection before that policy is approved. Jobs must respect the approved deletion/restriction fences and foundation restore safeguards. Provenance digests/IDs can be personal data and are subject to the same review.

## Measurable target proposal

Profile **T1** is a starting proposal for evaluation, **not an accepted target for Hulu, Netflix, or HBO**. For every provider verified by SUR-16, copy all rows into its acceptance record, select values against evidence, and obtain S4 approval. Do not substitute synthetic pass results for provider validation or pool providers to hide failures. Where a metric cannot be measured, record unavailable + reason and resolve launch scope; an empty denominator is not 100%.

| ID / dimension | Definition and proposed T1 threshold | Evidence / owner |
| --- | --- | --- |
| T1-C Completeness | 100% of expected accessible source occurrences in the approved window accounted for as persisted observation, confirmed duplicate, or explicitly quarantined; ≥99% normalized into events. Report missing, quarantine, unsupported and truncation counts separately. Neither quarantine nor a duplicate pointer to an absent event counts as normalized. Historical coverage beyond provider-accessible bounds is unknown. | Gold source inventory reconciled by stable keys/approved artifact locators, all pages and scope filters; SUR-23/SUR-24 |
| T1-M Match accuracy | ≥99% precision = correct automatically matched events / all automatically matched events; ≥95% coverage = correctly matched events / all gold-labelled catalog-resolvable movie/episode events. Measure movies and episodes separately; report unresolved, unsupported, catalog-unavailable and catalog-unresolvable counts. No title-only false positives in mandatory ambiguity fixtures. | Independent human-labelled provider sample with frozen catalog revision; SUR-22 |
| T1-D Duplicates/repeats | Zero extra persisted events from replay, overlap, reconnect or crash recovery under verified source keys; duplicate rate = erroneous extra events / expected distinct source events = 0 in the acceptance corpus. Zero incorrectly merged legitimate repeats. Unresolved overlap rate reported separately; every unresolved case labelled and no unsupported automatic merge. | Compare source identities/provenance and final event set, not only row counts; SUR-22/SUR-23/SUR-24 |
| T1-L First import | For 1,000 accessible records per selected scope, p95 ≤5 min; for 10,000, p95 ≤30 min. Start when authorization and scope selection are committed; end when all approved-window records are durable and query-visible, reconciliation/matching attempted, and honest terminal status visible. Queueing, catalog calls, quota waits and retries included. Time to first visible batch reported separately. | 30 independent runs per size/provider, cold checkpoint; SUR-23/SUR-27 |
| T1-F Freshness | p95 ≤8 h from first provider-accessible observation to durable/query-visible event, plus maximum delay ≤24 h in the release cohort. Measure watch-to-visibility separately only when source timestamps/publication evidence support it. Last successful sync age is a diagnostic, not event freshness. | Controlled source publication or bounded probe intervals; use earliest possible publication as conservative start and report interval uncertainty. 100 new source events over ≥7 days, including polling boundaries; SUR-24/SUR-27 |
| T1-V Volume | 1,000 synthetic app users, up to 3 accounts/provider/user, one selected scope/account; 10,000 records/scope and 30,000/provider/user. Reconcile exact expected totals; no silent truncation or corruption at the boundary. Above-limit behavior explicitly partial. | Production-equivalent storage test; generated distributions supplement provider sample, clearly labelled; SUR-19/SUR-27 |
| T1-N Concurrency | 20 queued/running imports across distinct users, maximum 5 executing/provider and 1/connection; remainder fairly queued. Latency gates still apply at this load. A lower provider quota requires revised approved capacity/latency values before launch. | 30-min load after 2-min ramp; healthy provider progresses while another is rate-limited; SUR-24/SUR-27 |
| T1-R Reliability | ≥99% eligible runs reconcile the approved window within 24 h over a rolling 30-day window, per provider. Numerator requires no missing/unresolved import failures; quarantined source errors make a run degraded and excluded from success numerator. Denominator includes every scheduled/admitted initial/manual run, including scheduler misses, outages, quota waits and timeouts. Repeated attempts count once per logical run. | At least 100 runs/provider over ≥7 days before release; then report actual 30-day production window. Pre-release evidence is not a monthly operating result; SUR-27 |
| T1-U Responsiveness | Refresh/enqueue acknowledgement p95 ≤1 s; first 50 private history rows plus sync status p95 ≤2 s under T1-N load and foundation N1 network conditions. Existing foundation budgets still apply to foundation journeys. | 30 trials per operation/provider, include authorization and persistence/read consistency; SUR-25/SUR-27 |

For T1-R, only owner-initiated disconnect/deletion/scope-change cancellations before completion and explicitly pre-disabled scheduling are excluded, with counts/reasons reported separately. Unexpected provider revocation/auth expiry remains a failed run and action-required outcome. Account restriction cancels safely and is reported separately. Coalesced manual requests are not extra runs. A provider outage and planned maintenance are not metric exclusions. Establish expected schedule slots independently of worker logs so lost jobs cannot disappear from the denominator.

Measurement protocol:

1. Freeze contract/adapter/matcher/catalog revisions, exact provider access method and region, approved window/limits/quotas, service tiers, worker configuration, test dates and reference network from SUR-6. Use authorized controlled accounts under approved SUR-18 handling; load tests use synthetic records when provider terms/quotas prohibit production-volume traffic. Report synthetic adapter throughput separately from live end-to-end evidence; both are needed where applicable.
2. For C/M/D, use at least 1,000 labelled source occurrences/provider, including at least 200 movies and 200 episodes if both are in launch scope, plus all mandatory fixtures. Include languages, remakes, specials, repeats, sparse timestamps and overlapping imports present in provider evidence. If available samples are smaller or a content type unavailable, record the limitation and revise S4 scope/sample requirements explicitly; do not silently declare a pass.
3. For latency use nearest-rank p95 (`ceil(0.95 × n)`, rank 29 for 30), record p50/p95/max and all raw redacted durations/outcomes. Failed/time-out trials count as infinite latency and remain in the denominator; additionally require all 30 nominal-path runs to complete. Run each size both idle and under concurrency; never combine cohorts to obscure a failure. Refresh/read trials apply N1 at the client; provider network conditions are measured and recorded, not assumed equivalent to N1.
4. Repeat exact inputs three times, then overlap windows/pages, reconnect, interrupt before/after commit, expire a cursor, change source payload, revoke access during commit, inject 429/5xx and exhaust retry budget. Require stable IDs/provenance, correct partial states, no lost records, no unauthorized commit, and independent healthy-provider progress. Safety/corruption failures block acceptance regardless of aggregate percentages.
5. SUR-27 records per-provider counts, coverage bounds, match/duplicate outcomes, queue/import delays, freshness, retry exhaustion, failure reasons and recovery evidence. Reuse SUR-13 diagnostics; provider/status buckets and transient correlation IDs only in general telemetry, no tokens, titles, account/profile identifiers or raw history. Restricted reconciliation evidence follows SUR-18. Name operations primary/backup, alert thresholds and runbook links through S4, without replacing SUR-6 operations policy.
