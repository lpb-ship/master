## Release sequence

Each stage requires a named executor, timestamp, artifact/configuration/schema revisions, evidence link and explicit pass/hold decision in the release record. The actual commands and service-specific ordering must be supplied by the tested dependency runbooks; do not improvise them from this outline. Missing safe controls block the affected stage.

1. **Freeze and gate.** Obtain the approved SUR-59 scope, SUR-63 approval for the candidate, accepted owners, configuration results, dependency evidence, recovery objectives and monitoring windows. Record the exact candidate and previous compatible artifacts, schema/job payload compatibility, provider configuration versions and verified recovery point. Confirm support and rollback coverage for the full window. Do not begin while any blocker below is open.
2. **Quiesce affected writes.** Use tested controls to hold new sync scheduling, affected callbacks and job/derived-state producers; drain or fence in-flight workers and record queue/checkpoint state. Define how callbacks are durably buffered or retried without losing events. Keep privacy enforcement and restriction/deletion capture operating. If a required privacy path cannot stay safe, deny affected reads/writes under the approved maintenance procedure.
3. **Prepare data and deploy application.** Use the existing migration/deployment runbooks with serialized migrations and proven compatibility for old/new application and worker versions. Prefer the approved backward-compatible expansion path; do not run destructive schema contraction during the rollback window. An incompatible change requires SUR-14's tested forward-repair/restore route before release. Keep new integrations and shared/derived consumers gated while checking the application and auth/profile persistence/denial paths.
4. **Validate integrations and resume activity cautiously.** Check production provider permissions and callbacks with controlled accounts. Enable the approved canary scope, compatible workers and limited ingestion; reconcile cursor/checkpoint ownership, idempotency, late callbacks, partial imports and freshness before increasing work. Confirm private/default visibility and deletion/restriction propagation before activity reaches shared consumers.
5. **Enable social and discovery consumers.** Apply current restrictions and deletion records before building or serving derived state. Validate permitted and denied reads and revocation across caches, feed and recommendations; require SUR-46 approval before enabling the feed prerequisite-dependent surface. Enable approved discovery sources and verify source-aware metrics and watchlist persistence. Do not reuse stale social caches merely because application health is green.
6. **Expand and hand off.** Expand only through SUR-59-approved cohorts after each agreed observation window passes; execute the stitched launch journeys and failure/empty-state checks. SUR-64 owns publication and production journey verification. Keep the previous compatible artifact and recovery coverage for the approved rollback window; record support/monitoring acceptance, residual nonblocking risks and the next review time. Resume each held producer explicitly and verify no orphaned queue or disabled alert remains.

## Rollback and recovery sequence

1. **Declare and contain.** The accepted authority records the trigger, incident start, affected scope and rollback decision. Hold expansion and unsafe traffic; disable affected shared/derived reads on suspected exposure. Pause/fence activity scheduling, callback writes, workers and derived rebuilds using the tested runbooks; preserve durable backlog and checkpoint information. Keep privacy restriction/deletion intake and enforcement safe, or deny affected operations. Support communicates the verified impact.
2. **Choose a tested recovery path.** Foundation/data operators compare the current schema, data semantics, job payloads and provider configuration with the previous artifact. For proven compatibility, restore the matching application/configuration and compatible worker versions while work remains held. Do not restore revoked/compromised credentials or unsafe callback settings. For incompatibility, keep containment and invoke SUR-14's tested forward repair or restore procedure; application rollback alone cannot undo data mutations. Record expected data loss and approved RPO/RTO comparison before a restore.
3. **Recover canonical state and privacy restrictions.** Execute the linked foundation procedure without repeating its implementation here. For a restore, use an isolated target and independently retained deletion/restriction records; reconcile identity mappings, sessions, provider connection/revocation state, activity checkpoints and canonical watchlist writes. Invalidate restored sessions/tokens as prescribed. Never re-enable an account, connection, deleted activity or sharing grant solely because an older snapshot contains it. Missing durable restriction/deletion records is a hard stop.
4. **Reconcile derived state before serving it.** Privacy/social and discovery operators invalidate affected caches, feeds, indexes and recommendations, then rebuild only from reconciled canonical data under current permissions. Reapply tombstones/revocations before reads. Reconcile or quarantine delayed callbacks/jobs using idempotency and schema rules so they cannot resurrect removed activity or duplicate imports. Keep affected surfaces denied until the owner/friend/unauthorized and propagation checks pass; a non-social fallback requires prior scope approval.
5. **Validate and resume in dependency order.** Verify foundation/application persistence and denial checks first, then current provider access and bounded activity processing, then social/discovery state and end-to-end journeys. Resume producers/consumers in the runbook's controlled order with monitoring active and explicit checkpoint ownership. The rollback authority and privacy owner must accept the relevant results before restoring shared reads or expanding traffic. Repeat approved observation windows; a failed check keeps containment in place.
6. **Close the operational handoff.** Record actual recovery time/data loss against approved objectives, final artifact/schema/configuration versions, backlog and derived-state disposition, support communications and follow-up owners. Route defects and changed evidence to SUR-63 for retest and a new release decision; do not automatically retry the failed release.
