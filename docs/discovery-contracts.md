## Canonical identity and save semantics

The shared catalog authority owns immutable opaque `catalogEntityId` values and the versioned mapping `(catalogNamespace, entityType, externalId) → catalogEntityId`. Source namespaces must distinguish service/environment and territory where IDs require it. Display titles, translated titles, release years, season numbers, URLs and provider IDs alone are never internal identity keys. Discovery consumes the same resolver for all surfaces.

Extend SUR-17's movie/episode model with `series`, `season`, and `edition` references. Each reference carries `entityType`, `catalogEntityId`, mapping revision and evidence; seasons link to a confirmed series, episodes link to confirmed series/season where available, and editions link to a confirmed base work. Missing parents remain unresolved, not fabricated. An edition is an evidenced cut/release variant; dubbing, artwork, device format or offer type does not automatically create a different work. Do not add a parallel catalog or generate a synthetic canonical ID for a failed match.

| Input | Search/detail/recommendation identity | Proposed watchlist target | Availability boundary |
| --- | --- | --- | --- |
| Movie; remake with the same title | Each evidenced movie keeps its own ID; year/kind distinguish presentation | Movie ID | Exact movie and any evidenced edition scope |
| Series | Series ID; never a synthetic episode | Series ID | Series offer must disclose whether coverage is whole, partial or unknown |
| Season, including specials | Season ID with evidenced series parent; numbers are labels | Parent series ID, explicitly labelled “Save series” | Season offer covers only the identified season; no whole-series inference |
| Episode | Existing SUR-17/SUR-22 episode ID; parent mapping enables series discovery without changing the viewing event | Parent series ID, explicitly labelled “Save series” | Episode-only offer never implies season or series access |
| Edition/cut | Edition ID and confirmed base movie/series; show distinguishing label | Base movie/series ID, explicitly labelled with the saved work | Preserve edition-specific offers; never transfer them to a different cut |
| Ambiguous/unmatched/unsupported identity or unresolved parent | Preserve safe source label and reason; no confirmed recommendation identity | No canonical save until resolved; explain unavailable save | No claimed offer for an arbitrary candidate |

This initial watchlist proposal saves movies and series, not separate seasons/episodes/editions. A detail view can retain selected season/edition as navigation context, but must show the actual saved target before the action. Independent season/edition saves require an explicit C1 scope decision and revised uniqueness/UX tests before implementation.

Every resolved card/detail carries a shared projection: canonical reference, display title/kind, available distinguishing year/parent/edition label, `mappingRevision`, nullable `saveTarget`, and safe resolution state/reason. Search → details → recommendation → watchlist must resolve to the same target at the same revision. Localization and metadata refresh never change it. Missing artwork or descriptions use honest text/visual fallbacks without changing identity. Stale search responses cannot replace a newer query or region selection.

[SUR-50](https://linear.app/lb-sandbox/issue/SUR-50) owns private persistence and atomic uniqueness on `(server-derived appUserId, resolved saveTarget catalogEntityId)` across every entry point. Add is idempotent and returns the existing item for concurrent duplicate saves. Remove is idempotent; conflicting add/remove operations require a version check and reconciliation. A watchlist item retains a stable item ID, canonical target, server version and creation time; client-generated labels/IDs are not authoritative. Acknowledged save means committed persistence; reload/sign-in must recover it.

Catalog aliases must resolve before read/write uniqueness checks. A proven catalog merge needs a versioned alias and transactional reconciliation of duplicate saves, preserving one stable item and deterministic aliases to prior items. Catalog splits or disputed merges require review; never silently move a save to an arbitrary candidate. Removed/unresolvable catalog entries remain an owner-visible unavailable item that can be removed. Repair mappings without changing SUR-22 `eventId`, source provenance, or repeat-watch counts. Source outage is not a catalog deletion. Alias/migration ownership and conflict behavior require C1 approval before shipping remaps.

## Region, coverage, and availability

Region is a user-selected supported market, represented by the code system approved with SUR-34. Carry it explicitly through search filters, details, recommendations, offers and watchlist availability. Language/locale, account country and provider profile are separate fields; neither language nor a connection proves current region. Do not silently infer a market from IP or device location. Unknown region prompts selection while allowing metadata-only discovery when licensed. Unsupported region shows a coverage limitation, never “not available anywhere.” Region persistence/location policy remains C2/C4; until approved, use session navigation context without adding profile fields.

| Logical contract | Required information and semantics |
| --- | --- |
| Coverage context | Source and policy revisions; supported region/provider/platform/language/entity/offer-type matrix; coverage `validated`, `partial`, `unsupported` or `unverified`; source evidence/attribution and permitted-use references from SUR-34. Only validated scope may claim a complete negative result. |
| Offer observation | Canonical entity and exact season/episode/edition scope; provider namespace and source offer reference; region; platform restrictions; `offerType` = `subscription_included`, `rental`, `purchase`, `ad_supported` or `unknown`; nullable tier/add-on requirement; source evidence, `observedAt`, nullable source update/validity times, and freshness-policy revision. Unknown fields stay unknown. |
| Availability result | `available`, `not_available`, `unknown` or `unsupported`; freshness `current`, `stale` or `unknown`; coverage context, offers, partial/error reason and observation time. `not_available` requires a successful, current, authoritative negative for the exact supported scope; an empty response from a partial source is unknown. |
| Destination | Source-qualified validated destination and its entity/region/platform scope; validation state/time supplied by [SUR-48](https://linear.app/lb-sandbox/issue/SUR-48). A safe provider landing/search fallback must be labelled as such. A link alone proves neither availability nor entitlement. |

Offers must remain separate by type, provider, territory and content scope. A connected or active subscription cannot convert rental/purchase/ad-supported offers into included access. Subscription relevance is a derived annotation: `included_match` only when current subscription evidence and the exact current offer/tier/region agree; otherwise `provider_match` with an explicit entitlement caveat, `unknown`, or `no_match` where evidence supports it. Even an included match is source-reported relevance, not a playback guarantee. Unknown tier or bundle coverage prevents an included claim. Multiple accounts remain separate observations; do not let one inactive account overwrite another account's active evidence.

Revalidate on region changes, input/policy revision changes, known offer expiry or source invalidation. Source refresh schedules, permitted cache lifetimes and stale display windows require SUR-34 approval; no TTL is chosen here. Current status requires a valid approved policy and evidence within all applicable deadlines. Missing policy/timestamps cannot mean current. A stale observation may be displayed with its time and warning only when rights permit; otherwise suppress it. Expired/stale offers cannot retain a current included badge or definitive negative. Keep metadata/watchlist operations usable during availability outages and show availability unknown. Do not fall back to another territory or provider's claims.

## Subscription and taste consumer interfaces

Streaming owns connections, subscription observations, imports, provenance and history. Discovery uses an authorized read projection, never raw tables/credentials, and does not write subscription fields or start its own import loop. Subscription information is account-scoped; taste inputs remain tied to the explicitly selected provider scope. Connection authorization is neither paid subscription evidence nor permission to use history for recommendations.

Proposed streaming adapter result `readDiscoveryInputs()` is bound to the trusted session, not a client actor ID. It includes a revision, policy/use authorization, observation/freshness metadata, selected-scope provenance, and separate results for subscriptions and taste. Each result distinguishes `ready`, `partial`, `empty`, `stale`, `unavailable` and `not_permitted`, with a safe reason. Empty means a successful authorized read with no eligible inputs, not a failed read. This projection is required integration work under C3, not a claim that SUR-19 exposes an API today.

| Input | Permitted projection/use | Updates and missing/stale behavior |
| --- | --- | --- |
| Subscription | SUR-17 `state`, `basis`, source-qualified provider, necessary tier/entitlement fields, `observedAt`, validity/freshness policy and field-availability reasons. Use only for the owner's filtering/ranking and qualified relevance labels. Discovery does not need payment details or billing dates. User assertions remain outside SUR-17 v1. | Use committed upstream revisions after refresh/reconnect; unknown/unavailable never becomes inactive. On stale/missing data, remove current entitlement claims and offer unpersonalized provider filters with an explanation. |
| Connection | Safe owner-visible connection state/limitation and link to existing SUR-21 controls. No provider account/profile keys, tokens or raw errors. | Keep disconnected, authorizing, connected and action-required distinct. A successful connection does not mean sync completion. Reconnect/disconnect are streaming actions; discovery refreshes its projection after their acknowledged outcome. |
| Taste | Purpose-authorized own matched movie/episode references, safe mapping/provenance revisions, coverage/match quality and update time. A minimised derived feature projection is preferable to copying events. Use for private recommendations only under approved streaming/privacy policy. No other-user history or hidden-title explanations without a separate authorized projection. | Partial import can provide qualified signals if policy permits. Exclude ambiguous/unmatched/unsupported identities and unresolved overlap from asserted watch counts; do not reinterpret unknown timestamps as recent viewing. Exact sample sufficiency, signal weighting and staleness require C3/C5; no threshold is invented. |

Discovery must not rerun normalization, deduplicate viewing events, infer ratings/completion from a watch record, or describe an episode observation as completion of a whole series. Mapping a matched episode to a confirmed parent for recommendation grouping leaves the event unchanged. Account-level “viewer unknown” history cannot be presented as the user's personal taste without the upstream scope acknowledgement and permitted-use decision.

Fallback order for [SUR-53](https://linear.app/lb-sandbox/issue/SUR-53): use current authorized inputs; use partial inputs only with an explicit limited-basis label and policy approval; otherwise show licensed non-personal discovery/search with optional explicit filters. Popular/editorial lists are allowed only if SUR-34 validates that source/use, not assumed available. No history, too little usable history, stale input, provider outage and denied use each have a truthful explanation; none should strand search or imply a successful personalized result. If no licensed fallback exists, show a clear unavailable state and retry path.

Projection versions must change on relevant subscription, match, scope, import, consent, hidden-title, deletion and revocation updates. Invalidate affected derived results and recheck authorization before serving or committing a delayed response; ignore responses from an old user/scope/region/revision. Revocation, disconnect, deletion or policy denial stops use immediately at the data boundary even if an old result is cached. Do not use stale personal input as an outage fallback after authorization is lost. SUR-19 currently denies all imported-data reads for terminal connections; discovery must honor that stricter behavior. Erasure of derived data follows the approved lifecycle policy; denial is not evidence of physical deletion.

Private caches must be scoped to actor, permitted purpose/policy revision, input revision, scope and region, cleared on logout/account switch, and never shared publicly. Catalog-only cache sharing is allowed only under approved source rights. No raw queries, title/history lists, subscription details, stable user IDs or provider payloads in telemetry; [SUR-57](https://linear.app/lb-sandbox/issue/SUR-57) must use the SUR-6 allowlist and obtain review for additional aggregates. Recommendation services/processors and retention require SUR-6 Q5–Q7/privacy review before personal input leaves the existing boundary.

## Foundation integration and failures

Compatibility with the written SUR-5 proposal is confirmed at the requirements level only. Runtime integration and stakeholder confirmation from SUR-11/SUR-21 remain blocked.

- Use `resolveSession()` and server-derived `appUserId`; the storage `account_id` mapping belongs to foundation/streaming adapters. No new account/profile schema or client-selected owner. Every private read/write checks active account, ownership and policy at the data boundary.
- Reuse reserved `/discover`, `/watchlist` and `/connections` destinations. They require verified, complete profiles in SUR-5. Public catalog routes and detail subroute names are not approved; C4 must settle them with SUR-11. Preserve allowlisted internal destinations across authentication, recheck permission, and never replay a save automatically. Unimplemented features remain honest placeholders.
- Show non-personal loading while session resolves. Expiry/revocation clears private results/drafts and offers sign-in; verification/profile completion follows foundation routing. An authorization outage returns retryable `UNAVAILABLE`, not anonymous. Restricted/deleting accounts cannot read cached recommendations or mutate lists.
- Use foundation `UNAUTHENTICATED`, `VERIFICATION_REQUIRED`, `PROFILE_INCOMPLETE`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, `CONFLICT`, `RATE_LIMITED`, and `UNAVAILABLE` with safe messages/retry timing/correlation IDs. Missing and inaccessible private targets remain indistinguishable. Distinguish successful zero search results from failed/partial source fetches and unknown availability.
- Save acknowledgement requires durable commit; on a lost response, read/reconcile the canonical target before a bounded idempotent retry. Preserve visible input during a transient failure only while the session is valid. Offline/unconfirmed mutations never display “saved.” C4 must agree the concrete watchlist operation/version interface with SUR-50.
- Route transitions announce the destination and move/restore focus predictably. Search updates must not steal typing focus; loading/result counts, unknown availability, save outcomes and errors need accessible feedback. Keyboard users must operate filters, save/remove and outbound links; visible labels distinguish saving a series from viewing a season.

Reuse its production-equivalent staging, fixed runner/device/region/version evidence, cold/repeat cohorts, nearest-rank percentiles, raw redacted samples and failure accounting. Use SUR-6's protocol as the baseline, with discovery-specific cohorts/load explicitly approved under C5. Report sample counts, latency distributions, failures/timeouts and cold/warm results separately; never omit slow/error attempts or treat degraded output as a successful definitive result. Source rights restrict load tests as well as production calls. Functional synthetic tests can proceed before numeric agreement; passing them cannot satisfy performance/freshness release gates. An unset target is a blocker, not unlimited time or a passing result.

These are synthetic review cases and future test requirements, **not executed application tests**. [SUR-38](https://linear.app/lb-sandbox/issue/SUR-38), [SUR-40](https://linear.app/lb-sandbox/issue/SUR-40), SUR-48, SUR-50 and SUR-53 implement their surfaces; [SUR-58](https://linear.app/lb-sandbox/issue/SUR-58) verifies the integrated journey.
